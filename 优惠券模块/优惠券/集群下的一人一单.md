# 问题
![[Pasted image 20260804173926.png]]
项目部署在多台服务器上，负载均衡把请求分发到不同机器。

两个请求同时到达不同服务器：

- 服务器1的线程获取了synchronized锁，开始执行业务
    
- 服务器2的线程也获取了synchronized锁，也开始执行业务
    
- 两台服务器的锁完全独立，互不影响
    
- 结果：一人一单再次失效


**问题本质**：synchronized是JVM级别的锁，锁信息在各自进程的内存里，跨进程就管不到了。

**需要换一种锁**：需要一个所有服务器都能访问到的公共存储来存放锁信息。Redis就是常用的选择。

#### 到底该用哪个命令？

**不要用 `SETNX`，要用 `SET` 命令的扩展参数。**

**正确的加锁命令：**
```redis
SET lock_key client_id NX PX 30000
```

**原因非常关键：**

过去用 `SETNX` 加锁后，需要再单独发一条 `EXPIRE` 设置过期。这是两步非原子操作，极其危险：如果在 `SETNX` 成功后，`EXPIRE` 发出前客户端崩溃了，这个锁就**永远无法过期**，导致整个系统死锁。

而 `SET ... NX PX` 是一条命令，Redis原子地完成了“抢锁 + 设置过期时间”这两件事。

- **`NX`**：就是原来 `SETNX` 的 `NX` 语义，Key不存在才设置。
    
- **`PX 30000`**：同时给这个Key设置30秒的过期时间。EX也行

# 项目中实现redis分布式锁

## 初版

一人一单
redis锁的工具类
```java
public class SimpleRedisLock implements Lock {

    /**
     * RedisTemplate
     */
    private StringRedisTemplate stringRedisTemplate;

    /**
     * 锁的名称
     */
    private String name;
	//构造方法
    public SimpleRedisLock(StringRedisTemplate stringRedisTemplate, String name) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.name = name;
    }


    /**
     * 获取锁
     *
     * @param timeoutSec 超时时间
     * @return
     */
    @Override
    public boolean tryLock(long timeoutSec) {
        String id = Thread.currentThread().getId() + "";
        // SET lock:name id EX timeoutSec NX
        Boolean result = stringRedisTemplate.opsForValue()
                .setIfAbsent("lock:" + name, id, timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(result);
    }

    /**
     * 释放锁
     */
    @Override
    public void unlock() {
        stringRedisTemplate.delete("lock:" + name);
    }
}
```

业务流程中使用redis分布式锁实现一人一单防止超卖
```java
        // 3、创建订单（使用分布式锁）
        Long userId = ThreadLocalUtls.getUser().getId();
        SimpleRedisLock lock = new SimpleRedisLock(stringRedisTemplate, "order:" + userId);
        boolean isLock = lock.tryLock(1200);
        if (!isLock) {
            // 索取锁失败，重试或者直接抛异常（这个业务是一人一单，所以直接返回失败信息）
            return Result.fail("一人只能下一单");
        }
        try {
            // 索取锁成功，创建代理对象，使用代理对象调用第三方事务方法， 防止事务失效
            IVoucherOrderService proxy = (IVoucherOrderService) AopContext.currentProxy();
            return proxy.createVoucherOrder(userId, voucherId);
        } finally {
            lock.unlock();
        }
```

`try...finally...`确保发生异常时锁能够释放，注意这给地方不要使用`catch`，A事务方法内部调用B事务方法，A事务方法不能够直接catch，否则会导致事务失效


## 优化1

### **问题**：
上一节，我们实现了一个简单的分布式锁，但是会存在一个问题：当线程1获取锁后，由于业务阻塞，线程1的锁超时释放了，这时候线程2趁虚而入拿到了锁，然后此时线程1业务完成了，然后把线程2刚刚获取的锁给释放了，这时候线程3又趁虚而入拿到了锁，这就导致又出现了超卖问题

这个问题描述的场景，就是典型的**锁误删引发连锁反应**，最终导致分布式锁完全失效。

一步步拆解这个“连锁车祸现场”：

	场景还原（假设锁过期时间10秒）

**时间线**：

| 时间点 | 线程1 | 线程2 | 线程3 | Redis中的锁 |
|:---|:---|:---|:---|:---|
| 第0秒 | 抢到锁，开始业务 | 等待 | 等待 | 线程1持有 |
| 第10秒 | 业务还没做完（阻塞） | — | — | **锁自动过期被删** |
| 第11秒 | 仍在做业务 | **趁虚而入抢到锁** | 等待 | 线程2持有 |
| 第13秒 | **业务终于完成，执行解锁** | 正在做业务 | 等待 | **被线程1误删！** |
| 第14秒 | 结束 | 业务还在做（但锁没了） | **趁虚而入抢到锁** | 线程3持有 |
| 第15秒 | — | 业务完成，执行解锁 | 正在做业务 | **被线程2误删！** |


	逐帧分析

**第一幕：线程1超时**
线程1业务阻塞（比如调第三方接口卡住了），10秒后锁自动过期。这是Redis防止死锁的保护机制，本身没问题。

**第二幕：线程2趁虚而入**
锁过期后，线程2立刻抢到锁，开始执行同一个业务（比如给同一用户下单）。**此时线程1和线程2同时在操作同一资源**，锁已经失效了。

**第三幕：线程1误删**
线程1终于恢复，走到`finally`块里的`delete`代码。**它没有任何校验，直接删掉了锁**。但这个锁已经是线程2的了。
**后果**：线程2的锁被删，它还在跑业务，锁的保护却没了。

**第四幕：线程3趁虚而入**
线程3发现没有锁，立刻抢到，也开始操作同一资源。**此时线程2和线程3又在同时操作**，锁再次失效。

**连锁反应**：
`超卖`只是表象，本质是：**一旦发生一次锁超时释放，由于无校验的误删，会导致后续的锁持有者一个接一个地被“误杀”，锁的保护作用完全瘫痪**。卖10张优惠券，最终可能被20个人买走。


	根因与解决思路

**根因**：
解锁时没有校验“这把锁还是不是我的”，直接无脑`DEL`。

这正好对应上面提到的**第一次优化**：存线程标识 + 解锁时先判断是不是自己的锁。但即便判断了，判断和删除不是原子的，依然会在极端情况下误删。彻底的解决方案是**用Lua脚本把判断和删除打包成原子操作**，那部分我们之前也聊过了。

### 代码优化
如何解决呢？我们为分布式锁添加一个线程标识，在释放锁时判断当前锁是否是自己的锁，是自己的就直接释放，不是自己的就不释放锁，从而解决多个线程同时获得锁的情况导致出现超卖
```java
/**
 * @title
 * @description
 */
public class SimpleRedisLock implements Lock {

    /**
     * RedisTemplate
     */
    private StringRedisTemplate stringRedisTemplate;

    /**
     * 锁的名称
     */
    private String name;
    /**
     * key前缀
     */
    public static final String KEY_PREFIX = "lock:";
    /**
     * ID前缀
     */
    public static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";

    public SimpleRedisLock(StringRedisTemplate stringRedisTemplate, String name) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.name = name;
    }


    /**
     * 获取锁
     *
     * @param timeoutSec 超时时间
     * @return
     */
    @Override
    public boolean tryLock(long timeoutSec) {
        String threadId = ID_PREFIX + Thread.currentThread().getId() + "";
        // SET lock:name id EX timeoutSec NX
        Boolean result = stringRedisTemplate.opsForValue()
                .setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(result);
    }

    /**
     * 释放锁
     */
    @Override
    public void unlock() {
        // 判断 锁的线程标识 是否与 当前线程一致
        String currentThreadFlag = ID_PREFIX + Thread.currentThread().getId();
        String redisThreadFlag = stringRedisTemplate.opsForValue().get(KEY_PREFIX + name);
        if (currentThreadFlag != null && currentThreadFlag.equals(redisThreadFlag)) {
            // 一致，说明当前的锁就是当前线程的锁，可以直接释放
            stringRedisTemplate.delete(KEY_PREFIX + name);
        }
        // 不一致，不能释放
    }
}

```



## 优化2
### 问题
在上一节中，我们通过给锁添加一个线程标识，并且在释放锁时添加一个判断，从而防止锁超时释放产生的超卖问题，一定程度上解决了超卖问题，但是仍有可能发生超卖问题（出现超卖概率更低了）：当线程1获取锁，执行完业务然后并且判断完当前锁是自己的锁时，但就在此时发生了阻塞，结果锁被超时释放了，线程2立马就趁虚而入了，获得锁执行业务，但就在此时线程1阻塞完成，由于已经判断过锁，已经确定锁是自己的锁了，于是直接就删除了锁，结果删的是线程2的锁，这就又导致线程3趁虚而入了，从而继续发生超卖问题

```
时间轴：线程1在unlock()中执行

[已执行完业务，进入finally块]

T1: String redisThreadFlag = GET lock:order  ← 读到锁值是 "UUID-线程1"
T2: if (currentThreadFlag.equals(redisThreadFlag)) ← 判断成功，是true！
    ↑
    |  就在这一瞬间！锁在Redis中过期了！
    |  线程2的 SET lock:order UUID-线程2 NX EX 10 执行成功，抢到了锁！
    |  线程2开始执行扣库存业务...
    |
T3:     DELETE lock:order  ← 这一刀下去，删的是线程2的锁！

T4: 线程3：咦？没有锁！SET lock:order UUID-线程3 NX EX 10 成功！
    线程3也开始执行扣库存业务...
    
结果：线程2和线程3同时操作库存 → 超卖
```

简言之：判断与解锁没有原子化(非原子操作导致的时间窗口)

虽然这个情况发生的概率较低，但是怕什么来什么，还是要解决的

解决： Lua脚本原子化

### 代码
```java
/**
 * @title
 * @description
 */
public class SimpleRedisLock implements Lock {

    /**
     * RedisTemplate
     */
    private StringRedisTemplate stringRedisTemplate;

    /**
     * 锁的名称
     */
    private String name;
    /**
     * key前缀
     */
    private static final String KEY_PREFIX = "lock:";
    /**
     * ID前缀
     */
    private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";

    public SimpleRedisLock(StringRedisTemplate stringRedisTemplate, String name) {
        this.stringRedisTemplate = stringRedisTemplate;
        this.name = name;
    }


    /**
     * 获取锁
     *
     * @param timeoutSec 超时时间
     * @return
     */
    @Override
    public boolean tryLock(long timeoutSec) {
        String threadId = ID_PREFIX + Thread.currentThread().getId() + "";
        // SET lock:name id EX timeoutSec NX
        Boolean result = stringRedisTemplate.opsForValue()
                .setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(result);
    }

    /**
     * 加载Lua脚本
     */
    private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;

    static {
        UNLOCK_SCRIPT = new DefaultRedisScript<>();
        UNLOCK_SCRIPT.setLocation(new ClassPathResource("lua/unlock.lua"));
        UNLOCK_SCRIPT.setResultType(Long.class);
    }

    /**
     * 释放锁
     */
    @Override
    public void unlock() {
        // 执行lua脚本
        stringRedisTemplate.execute(
                UNLOCK_SCRIPT,
                Collections.singletonList(KEY_PREFIX + name),
                ID_PREFIX + Thread.currentThread().getId()
        );
    }
}

```
这段代码就是黑马点评中**分布式锁的最终优化版本**，已经解决了前面讨论的所有致命问题。我帮你梳理一下它好在哪里，以及还存在的细微问题。

#### 代码解析

一、这段代码解决了什么问题？

1. 加锁：原子化 + 防死锁
```java
Boolean result = stringRedisTemplate.opsForValue()
        .setIfAbsent(KEY_PREFIX + name, threadId, timeoutSec, TimeUnit.SECONDS);
```
-   `setIfAbsent`：对应 `SET NX`，保证互斥
-   `timeoutSec`：对应 `EX`，锁自带过期时间，防止客户端宕机死锁
-   `threadId`：存线程标识，为安全解锁做准备

2. 解锁：Lua脚本原子化
```java
stringRedisTemplate.execute(
        UNLOCK_SCRIPT,
        Collections.singletonList(KEY_PREFIX + name),
        ID_PREFIX + Thread.currentThread().getId()
);
```
-   Lua脚本内完成了 `GET` → 比较 → `DEL` 的原子操作
-   **彻底消灭了"判断完还没来得及删，锁就过期了"的时间窗口**

3. Lua脚本外部化
```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("lua/unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```
-   脚本放在 `resources/lua/unlock.lua` 文件中，而不是硬编码在Java字符串里
-   `static` 块只加载一次，性能更好
-   脚本内容应与之前讨论的一致：
```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```


二、代码中的细节要点

1. `Boolean.TRUE.equals(result)` —— 拆箱安全
```java
return Boolean.TRUE.equals(result);
```
`setIfAbsent` 返回的是 `Boolean` 包装类，可能为 `null`。直接用 `null` 做布尔判断会空指针。这样写能安全处理 `null` 的情况。
 
2. `ID_PREFIX` 使用 `UUID` —— 多节点区分
```java
private static final String ID_PREFIX = UUID.randomUUID().toString(true) + "-";
```
-   `UUID.randomUUID().toString(true)` 生成的是一个不带横线的32位字符串
-   它的作用是**区分不同的服务实例**。假如多台服务器部署同一个服务，线程ID可能会重复。加上UUID前缀后，线程标识变成 `"a1b2c3-42"`，全局唯一

3. `static` 加载脚本 —— 只解析一次
```java
static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("lua/unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```
Redis执行Lua脚本时，第一次会编译并缓存。但Java端提前加载脚本资源，可以避免每次解锁时重复读取文件。



三、仍然存在的潜在问题

1. 锁超时自动过期，业务还没执行完
**场景：**
线程1获取锁，设置10秒过期。但业务逻辑跑了15秒（比如调用外部接口超时）。锁在第10秒自动过期，线程2趁虚而入。**此时线程1和线程2同时在执行临界区代码。**

**这个问题Lua脚本解决不了**，因为它只在解锁时起作用。

**解决方案（进阶方向）：**
-   **看门狗机制（Redisson的做法）**：只要客户端还活着，定期给锁"续期"
-   **合理设置过期时间**：根据业务经验设置一个足够长的超时时间

2. 单节点Redis，如果主从切换锁会丢失
**场景：**
Redis主节点上线程1获取了锁，锁还没同步到从节点，主节点挂了。从节点升级为新主，线程2请求新主，**同一个锁又被线程2获取了**。

这个问题单体Redis无法解决，需要 **Redlock算法** 或 **ZooKeeper/etcd** 这类强一致性存储。


 四、总结

| 维度 | 基础版 | 第一次优化 | 最终版（这段代码） |
|:---|:---|:---|:---|
| 加锁 | `SETNX`（无过期） | `SET NX EX`（有过期） | `SET NX EX`（有过期） |
| 解锁 | 直接`DEL` | 先`GET`判断，再`DEL`（非原子） | **Lua脚本原子执行** |
| 线程标识 | 无 | 有 | 有（UUID + 线程ID） |
| 误删风险 | **极高** | **极低但存在** | **完全消除** |

这段代码是目前单体Redis分布式锁的**正确实现**，已经解决了原子解锁的问题。



#### lua脚本执行代码解析

一、这行代码在做什么？

**一句话：把一段 Lua 脚本发给 Redis 执行，传入锁的 Key 和当前线程标识，让 Redis 原子地完成“判断锁是不是我的 → 是就删除”。**

把一段 Lua 脚本 + 两个参数（锁的Key、线程标识）打包成一个请求，发给 Redis 执行。

二、方法签名

`StringRedisTemplate.execute()` 有多个重载版本，这里用的是：

```java
public <T> T execute(
    RedisScript<T> script,   // 要执行的Lua脚本
    List<K> keys,            // 脚本中 KEYS 数组的值
    Object... args           // 脚本中 ARGV 数组的值
)
```

-   **返回值**：`<T>` 由 `RedisScript<T>` 的泛型决定。这里脚本返回 `Long`，所以最终返回 `Long` 类型
-   **作用**：序列化参数，发给 Redis，执行 `EVALSHA` 或 `EVAL` 命令

三、三个参数逐个解析

参数1：`UNLOCK_SCRIPT`

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;
static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("lua/unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```

-   `DefaultRedisScript`：Spring 封装好的 Redis 脚本类
-   `setLocation(...)`：指定脚本文件路径，这里是 `resources/lua/unlock.lua`
-   `setResultType(Long.class)`：告诉 Spring，Lua 脚本的返回值对应 Java 的 `Long` 类型

**加载的脚本内容：**

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

-   删锁成功返回 `1`（`DEL` 的返回值）
-   不是自己的锁返回 `0`


参数2：`Collections.singletonList(KEY_PREFIX + name)`

这就是传给 Lua 脚本的 **`KEYS` 数组**。

-   `Collections.singletonList(...)`：创建一个**不可变的单元素List**
-   `KEY_PREFIX + name`：例如 `"lock:order:1001"`

**对应关系：**

```lua
KEYS[1] = "lock:order:1001"   -- 这是Java传入的第1个参数
```

**为什么用 List 而不是直接传 String？**
Spring 的 API 设计统一用 `List<K>` 接收 Keys，一个脚本可能操作多个 Key。虽然这里只操作一个，也要包装成 List。

**为什么用 `singletonList` 而不是 `Arrays.asList`？**
-   `singletonList`：只有一个元素，内存更省，且明确表达“这个列表不会变”
-   `Arrays.asList`：也是不可变 List，但用于多个元素的场景更自然
-   这里功能上没区别，`singletonList` 更语义化


参数3：`ID_PREFIX + Thread.currentThread().getId()`

这是传给 Lua 脚本的 **`ARGV` 数组**（可变参数，可以传多个）。

-   `ID_PREFIX`：`UUID.randomUUID().toString(true) + "-"`
    例：`"a1b2c3d4e5f6-"`
-   `Thread.currentThread().getId()`：当前Java线程的ID
    例：`42`
-   拼接结果：`"a1b2c3d4e5f6-42"`

**对应关系：**

```lua
ARGV[1] = "a1b2c3d4e5f6-42"   -- 这是Java传入的第2个参数
```



四、完整的执行流程图

```
Java应用                              Redis服务器
   |                                      |
   |--- EVALSHA <脚本SHA1> 1 ------------->|
   |    lock:order:1001                    |
   |    a1b2c3d4e5f6-42                   |
   |                                      |
   |         1. 根据SHA1找到缓存的Lua脚本
   |         2. 把参数塞进去：
   |            KEYS[1] = "lock:order:1001"
   |            ARGV[1] = "a1b2c3d4e5f6-42"
   |         3. 单线程执行Lua脚本：
   |            GET lock:order:1001 → "a1b2c3d4e5f6-42"
   |            比较：相等！
   |            DEL lock:order:1001 → 成功
   |         4. 返回 1
   |                                      |
   |<-------- 返回 1 ---------------------|
   |
   ↓
result = 1L  (Long类型)
```


五、参数对应关系速查表

| Java传入 | Lua脚本中取值 | 实际值示例 | 说明 |
|:---|:---|:---|:---|
| `singletonList("lock:order:1001")` | `KEYS[1]` | `"lock:order:1001"` | 要操作的Redis Key |
| `"a1b2c3d4e5f6-42"` | `ARGV[1]` | `"a1b2c3d4e5f6-42"` | 当前线程的锁标识 |


六、为什么这么设计？

**本质：把“判断”和“删除”两个动作，从 Java 的两次网络调用，变成 Redis 内部的一次原子执行。**

```java
// 错误做法（两次网络调用，有时间窗口）
String value = redis.get("lock:order");  // 第1次
if (myId.equals(value)) {
    redis.del("lock:order");             // 第2次
}

// 正确做法（一次调用，Redis内部原子执行）
redis.execute(UNLOCK_SCRIPT, keys, myId);  // 整个判断+删除打包
```

这就是 Lua 脚本在分布式锁中的核心价值。
