##  为什么会产生超卖问题呢？
![[Pasted image 20260803174959.png|580]]

线程1查询库存，发现库存充足，创建订单，然后准备对库存进行扣减，但此时线程2和线程3也进行查询，同样发现库存充足，然后线程1执行完扣减操作后，库存变为了0，线程2和线程3同样完成了库存扣减操作，最终导致库存变成了负数！这就是超卖问题的完整流程

## 解决方案

那么我们该如何有效防止超卖问题的发生呢，以下提供几种常见的解决方案

超卖问题的常见解决方案：

**悲观锁**，认为线程安全问题一定会发生，因此操作数据库之前都需要先获取锁，确保线程串行执行。常见的悲观锁有：synchronized、lock
**乐观锁**，认为线程安全问题不一定发生，因此不加锁，只会在更新数据库的时候去判断有没有其它线程对数据进行修改，如果没有修改则认为是安全的，直接更新数据库中的数据即可，如果修改了则说明不安全，直接抛异常或者等待重试。常见的实现方式有：版本号法、CAS操作、乐观锁算法
悲观锁和乐观锁的比较

**悲观锁比乐观锁的性能低**：悲观锁需要先加锁再操作，而乐观锁不需要加锁，所以乐观锁通常具有更好的性能。
**悲观锁比乐观锁的冲突处理能力低**：悲观锁在冲突发生时直接阻塞其他线程，乐观锁则是在提交阶段检查冲突并进行重试。
**悲观锁比乐观锁的并发度低**：悲观锁存在锁粒度较大的问题，可能会限制并发性能；而乐观锁可以实现较高的并发度。
**应用场景**：两者都是互斥锁，悲观锁适合写入操作较多、冲突频繁的场景；乐观锁适合读取操作较多、冲突较少的场景。


## 乐观锁的实现方案
乐观锁（Optimistic Locking）假设数据在大多数情况下不会发生并发冲突，因此**在读取和修改数据时不会加锁**，只有在**提交更新时**才会检查数据在此期间是否被其他事务修改过。如果发生冲突，则拒绝更新并让业务选择重试或抛出异常。

核心实现方式有两种：**版本号（Version）机制** 和 **CAS（Compare And Swap）算法**。

### 一、 版本号（Version）机制（最常用）

在数据库表中增加一个整型字段 `version`，每次读取数据时将 `version` 一并读出；更新时将 `version + 1`，并带上读出的 `version` 作为更新条件。

#### 1. 数据库表设计

```SQL
CREATE TABLE t_goods (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50),
    stock INT,
    version INT DEFAULT 0 -- 增加版本号字段
);
```

#### 2. 业务更新流程

1. **读取数据**：`SELECT id, stock, version FROM t_goods WHERE id = 1;`（假设读到 `stock = 10`, `version = 1`）。
    
2. **内存修改**：计算扣减后的库存 `stock = 9`。
    
3. **提交更新**：将上次读到的 `version` 作为过滤条件。
    

```SQL
UPDATE t_goods 
SET stock = 9, version = version + 1 
WHERE id = 1 AND version = 1;
```

4. **结果校验**：
    
    - 如果返回影响行数等于 1，说明在此期间没有其他事务修改该行，更新成功。
        
    - 如果返回影响行数等于 0，说明 `version` 已被其他事务更新，本次操作失败（触发重试或提示用户）。
        

### 二、 时间戳（Timestamp）机制

原理与版本号机制完全一致，将 `version` 字段替换为精度较高的毫秒级时间戳字段 `update_time`。

```SQL
UPDATE t_goods 
SET stock = 9, update_time = NOW() 
WHERE id = 1 AND update_time = '2026-08-03 18:50:00.123';
```

> **缺陷**：如果多个并发请求在同一毫秒内完成读取和提交，可能导致时间戳相同，从而引发误判。因此生产环境中更推荐使用递增的整数 `version`。

### 三、 隐式 CAS / 状态条件更新

如果业务数据本身具备**递增/递减**特征或**单向状态变更**规则，可以不需要额外的 `version` 字段，直接利用 SQL 的谓词条件实现无锁并发控制。

#### 1. 扣减库存场景（避免超卖）

```SQL
UPDATE t_goods 
SET stock = stock - 1 
WHERE id = 1 AND stock >= 1; -- 保证库存大于等于要扣减的数量
```

#### 2. 状态机流转场景

```SQL
-- 确保订单只能从“待支付(1)”流转到“已支付(2)”
UPDATE t_order 
SET status = 2 
WHERE id = 1001 AND status = 1;
```

### 四、 代码层面的实现方式

#### 1. MyBatis / MyBatis-Plus

MyBatis-Plus 内置了乐观锁插件 `OptimisticLockerInnerInterceptor`。

- **实体类标注**：
    

```Java
public class Goods {
    private Long id;
    private String name;
    private Integer stock;

    @Version // 标注版本号字段
    private Integer version;
}
```

- **执行更新**：
    

```Java
// 1. 查询商品
Goods goods = goodsMapper.selectById(1L);
// 2. 修改业务属性
goods.setStock(goods.getStock() - 1);
// 3. 执行更新（MyBatis-Plus 会自动将 version 拼接到 WHERE 条件中并自增）
// 相当于 SQL: UPDATE t_goods SET stock=?, version=version+1 WHERE id=? AND version=?
int rows = goodsMapper.updateById(goods);
if (rows == 0) {
    // 处理重试逻辑或抛出业务异常
}
```

#### 2. Java 内存级 CAS (AtomicReference / AtomicInteger)

在 Java 底层，并发包 `java.util.concurrent.atomic` 依赖硬件 CPU 的 CAS 指令（如 `cmpxchg`）实现无锁并发：

```Java
AtomicInteger stock = new AtomicInteger(10);

// CAS 自旋重试逻辑
public void decrement() {
    int expect;
    int update;
    do {
        expect = stock.get();          // 读取期望值
        if (expect <= 0) return;
        update = expect - 1;           // 计算更新值
    } while (!stock.compareAndSet(expect, update)); // 原子对比并替换
}
```

### 乐观锁与悲观锁对比

| **维度**   | **乐观锁**           | **悲观锁 (FOR UPDATE / synchronized)** |
| -------- | ----------------- | ----------------------------------- |
| **加锁时机** | 不加锁，提交更新时检查       | 读数据时即加锁                             |
| **适用场景** | 读多写少、冲突频率低        | 写多读少、高并发强冲突                         |
| **吞吐量**  | 高                 | 较低（存在线程阻塞）                          |
| **典型问题** | 高并发下重试率高导致 CPU 消耗 | 容易产生死锁、排队阻塞                         |
|          |                   |                                     |
