---

## 一、业务场景与核心目标

**业务**：优惠券秒杀，核心要求有两个：

1. **库存不能超卖**（秒杀券数量有限）
2. **一人一单**（同一用户只能抢一次）

**演进主线**：随着系统从单体到集群、并发量从低到高，逐步暴露问题并优化。

---

## 二、单体系统阶段

### 1. 最简单实现（无锁）

**流程**：

```
用户请求 → 查库存 → 扣库存 → 创建订单 → 返回
```

**问题**：高并发下，多个线程同时查到库存 > 0，都去扣减，导致**超卖**。

---

### 2. 乐观锁解决超卖

**思路**：利用数据库的 `WHERE` 条件做版本检查，更新成功才认为抢到。

```sql
UPDATE seckill_voucher
SET stock = stock - 1
WHERE voucher_id = #{voucherId} AND stock > 0
```

- 更新行数 = 0 → 库存不足，抢购失败
- 更新行数 = 1 → 扣减成功

**优点**：实现简单，不需要加锁。
**局限**：只能解决“扣库存”这一步的原子性，无法解决“一人一单”的重复下单问题。

---

### 3. 业务变更：一人一单

**新需求**：同一用户只能抢一次。

**新问题**：需要先查订单表判断是否已存在该用户的订单，再决定是否下单。这是两个操作，无法用一条 SQL 原子完成。

```
线程1：查订单 → 用户A 没有 → 准备插入
线程2：查订单 → 用户A 没有 → 准备插入
线程1：插入成功
线程2：插入成功 ← 一人一单被打破
```

---

### 4. 悲观锁解决一人一单

**思路**：用 `synchronized` 将“查订单 + 创建订单”串行化。

```java
public synchronized Result createVoucherOrder(Long voucherId) {
    // 1. 查订单
    // 2. 没有 → 扣库存 + 创建订单
}
```

**优点**：同一时刻只有一个线程能进入，保证一人一单。
**局限**：`synchronized` 只能在**同一个 JVM 内**生效。

---

## 三、集群阶段

### 5. 集群部署后 synchronized 失效

**场景**：系统升级为集群，多个 JVM 实例同时运行。

**问题**：

```
JVM-1：线程1 拿到 synchronized 锁 → 查订单 → 没有 → 插入
JVM-2：线程2 拿到 synchronized 锁 → 查订单 → 没有 → 插入
                                      ↑ 两个 JVM 各锁各的，互不干扰
```

**结果**：一人一单再次被打破，出现超卖。

**根源**：锁的作用域只在单个 JVM 内，无法跨进程互斥。

---

### 6. 分布式锁解决集群互斥

**思路**：用 Redis 的 `SETNX` 实现跨进程的锁。

```java
// 加锁
Boolean lock = redis.setIfAbsent("lock:order:" + userId, "1");
// 解锁
redis.delete("lock:order:" + userId);
```

**优点**：多个 JVM 都去 Redis 争同一个 Key，实现跨进程互斥。
**问题**：

- 没有过期时间 → 线程崩溃导致死锁
- 锁超时释放 → 误删别人的锁

---

## 四、分布式锁优化

### 7. 加过期时间 + 线程标识

**加锁**：原子执行 `SET key value NX EX 30`

```java
redis.setIfAbsent("lock:order:" + userId, threadId, 30, TimeUnit.SECONDS);
```

- `NX`：不存在才设置
- `EX 30`：过期时间 30 秒，防止死锁
- `threadId`：存线程标识，解锁时校验

**解锁**：先判断锁是不是自己的，再删除

```java
String value = redis.get("lock:order:" + userId);
if (threadId.equals(value)) {
    redis.delete("lock:order:" + userId);
}
```

**新问题**：判断和删除不是原子操作，存在时间窗口，仍可能误删。

---

### 8. Lua 脚本原子解锁

**思路**：把 `GET + 判断 + DEL` 打包成 Lua 脚本，在 Redis 内部原子执行。

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

**优点**：彻底消除时间窗口，解决误删问题。
**新问题**：锁不可重入，同一线程再次加锁会自己阻塞自己。

---

### 9. Hash 结构实现可重入锁

**思路**：用 Redis Hash 存 `{线程标识: 重入次数}`。

```lua
-- 加锁
if (exists == 0) or (hexists == 1) then
    hincrby(key, threadId, 1);
    pexpire(key, 30000);
end

-- 解锁
hincrby(key, threadId, -1);
if (counter == 0) then
    del(key);
end
```

**优点**：支持可重入，Lua 保证原子性。

---

### 10. 引入 Redisson 解决全部锁问题

自己实现分布式锁已经触及天花板，引入 **Redisson**，它提供了：

| 问题 | Redisson 方案 |
|:---|:---|
| 锁超时释放 | **Watchdog** 自动续期（每 10 秒延长到 30 秒） |
| 不可重入 | **Hash 结构** + 计数器 |
| 不可重试 | **Pub/Sub + Semaphore** 等待唤醒 |
| 判断删除非原子 | **Lua 脚本**原子执行 |
| 主从切换丢锁 | **MultiLock / RedLock** |

```java
RLock lock = redissonClient.getLock("lock:order:" + userId);
lock.lock();
try {
    // 业务
} finally {
    lock.unlock();
}
```

## 五、秒杀性能优化

### 11. 性能瓶颈：所有请求直连数据库

即使有分布式锁，秒杀流程仍然每一步都查/写数据库：

```
用户请求 → 查数据库库存 → 查数据库订单 → 扣库存 → 创建订单
```

高并发下，数据库连接池被打满，性能极差。

---

### 12. Redis 前置校验 + 异步落库

**核心思想**：把数据库从“前台扛并发”变成“后台做持久化”。

#### 第一步：Redis Lua 原子校验

把“判断库存”和“判断一人一单”搬到 Redis，用 Lua 脚本原子完成：

```lua
-- 判断库存
if stock <= 0 then return -1 end
-- 判断一人一单
if SISMEMBER(userSet, userId) == 1 then return -2 end
-- 扣库存 + 标记用户
DECR stock
SADD userSet userId
return 0  -- 校验通过
```

#### 第二步：异步下单

校验通过后，不直接写数据库，而是：

1. 将订单消息放入**消息队列**（BlockingQueue / Redis Stream）
2. 立即返回“排队中”
3. 后台消费者慢慢落库

**效果**：Redis 扛住瞬时高并发，数据库压力平滑。

---

### 13. 阻塞队列 → Redis Stream

最初用 JVM 内存 `BlockingQueue`，但存在**服务重启消息丢失、集群不共享、无 ACK**等问题。

升级为 **Redis Stream**：

| 能力 | BlockingQueue | Redis Stream |
|:---|:---|:---|
| 持久化 | ❌ JVM 挂即丢 | ✅ Redis 持久化 |
| 跨进程共享 | ❌ | ✅ 多实例共享 |
| 消息确认 ACK | ❌ 取出即删 | ✅ XACK 确认 |
| 消费组分摊 | ❌ 单消费者 | ✅ 多消费者并行 |
| 故障恢复 | ❌ 无 | ✅ Pending List 重新投递 |

## 六、最终架构图

```
用户请求
    │
    ▼
Redis Lua 校验（原子）
  ├─ 库存判断
  ├─ 一人一单判断
  ├─ 扣库存（Redis）
  └─ 标记用户（Redis Set）
    │
    ├─ 校验失败 → 返回“库存不足/已下单”
    │
    └─ 校验通过
         │
         ▼
    生成订单ID → 封装消息 → XADD 到 Stream
         │
         ▼
    立即返回“排队中”
         │
         ▼
Redis Stream（消息队列）
    │
    ▼
消费组（多个消费者实例）
    │
    ├─ 消费者1：XREADGROUP 取消息 → Redisson 分布式锁 → 落库 → XACK
    ├─ 消费者2：XREADGROUP 取消息 → Redisson 分布式锁 → 落库 → XACK
    └─ 消费者3：...
```

## 七、演进总结表

| 阶段 | 问题 | 方案 | 关键技术 |
|:---|:---|:---|:---|
| 单体无锁 | 超卖 | 乐观锁 | `WHERE stock > 0` |
| 单体一人一单 | 重复下单 | 悲观锁 | `synchronized` |
| 集群 | 锁失效 | 分布式锁 | Redis `SETNX` |
| 锁优化1 | 死锁/误删 | 过期时间+线程标识 | `SET NX EX` |
| 锁优化2 | 非原子解锁 | Lua 脚本 | Redis Lua |
| 锁优化3 | 不可重入 | Hash 结构 | `hincrby` |
| 锁优化4 | 不可重试/续期 | Redisson | Watchdog + Pub/Sub |
| 性能优化 | 数据库压力大 | Redis 前置 + 异步 | Lua 校验 + MQ |
| 可靠性优化 | 队列不持久 | Redis Stream | XACK + 消费组 |

**核心演进思路**：**从单体到集群 → 从直接操作数据库到 Redis 前置 → 从自己造锁到使用成熟框架 → 从同步落库到异步削峰**。
