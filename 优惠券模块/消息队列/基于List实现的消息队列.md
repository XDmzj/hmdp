

## Redis List 实现消息队列

---

### 一、核心数据结构

Redis 的 `List` 是一个**双向链表**，天然支持从一端塞入、从另一端取出，正好对应消息队列的"生产者入队，消费者出队"。

```
生产者                    Redis List                  消费者
  │                         │                           │
  │  LPUSH queue "msg" ────→│  ["msg3","msg2","msg1"]    │
  │                         │                           │
  │                         │  BRPOP queue 0 ───────────→│
```

---

### 二、基本命令

| 角色 | 命令 | 说明 |
|:---|:---|:---|
| 生产者入队 | `LPUSH queue message` | 从左边塞入 |
| 消费者出队 | `RPOP queue` | 从右边取出（非阻塞，队列空返回 nil） |
| 消费者阻塞出队 | `BRPOP queue timeout` | 队列空时阻塞等待，timeout=0 表示永久等待 |
| 查看队列长度 | `LLEN queue` | 积压量监控 |
| 查看不消费 | `LRANGE queue 0 -1` | 只看不取 |

**最常用的搭配：`LPUSH` + `BRPOP`**

生产者用 `LPUSH` 塞入，消费者用 `BRPOP` 阻塞等待，队列空了消费者线程挂起，不空转 CPU。

---

### 三、Java 代码示例

```java
// 生产者
public void produce(String message) {
    stringRedisTemplate.opsForList().leftPush("order_queue", message);
}

// 消费者：用一个独立线程不停消费
public void consume() {
    while (true) {
        // BRPOP 阻塞等待，队列空时线程挂起
        String message = stringRedisTemplate.opsForList()
                .rightPop("order_queue", 0, TimeUnit.SECONDS);
        // 处理消息
        handleMessage(message);
    }
}
```

### 四、优缺点

#### 优点

| 优点           | 说明                     |
| :----------- | :--------------------- |
| **简单**       | 两个命令搞定，零学习成本           |
| **阻塞式消费**    | `BRPOP` 自动挂起线程，不空转 CPU |
| **复用 Redis** | 不用额外部署 MQ 软件           |
| **快**        | Redis 内存操作，单机十万级 QPS   |

#### 缺点

| 缺点 | 说明 |
|:---|:---|
| **消息确认缺失** | 消费者取出消息后崩溃，消息就**丢了**。没有 ACK 机制 |
| **持久化弱** | 若不开启 AOF，Redis 重启消息全丢 |
| **单消费者模型** | 一条消息只能被一个消费者取走（不支持消费组广播） |
| **不支持重复消费控制** | 业务层需要自己幂等 |
| **不支持延迟消息** | 取出就消费，没法定时 |
| **无死信队列** | 消费失败的消息没有自动重试/兜底机制 |

**最致命的缺点：消息丢失。** 专业 MQ（RabbitMQ/Kafka）有 ACK 机制，消费者处理完才确认消息，没确认前消息不会丢。Redis List 一 `BRPOP` 出去，消息就没了，哪怕你后面处理失败也找不回来。

### 五、适用场景

| 场景                   | 是否适合                         |
| :------------------- | :--------------------------- |
| 对消息丢失**不敏感**（如日志、通知） | ✅ 适合                         |
| 轻量级解耦、削峰             | ✅ 适合                         |
| 只有一组消费者              | ✅ 适合                         |
| 对消息**可靠性要求高**（订单、支付） | ❌ 不适合                        |
| 需要消费组 / 广播           | ❌ 不适合（用 Redis Stream 或专业 MQ） |
| 需要消息重试 / 死信          | ❌ 不适合                        |

---

### 六、和黑马点评中 `BlockingQueue` 的对比

| 维度    | JVM BlockingQueue | Redis List MQ     |
| :---- | :---------------- | :---------------- |
| 存储位置  | JVM 内存            | Redis 内存          |
| 服务重启  | 消息全丢              | 消息还在（若 Redis 不重启） |
| 跨 JVM | ❌ 不能              | ✅ 可以              |
| 阻塞消费  | `take()`          | `BRPOP`           |
| 性能    | 最快（本机内存）          | 快（网络开销）           |
| 可靠性   | 最低                | 稍好，但仍无 ACK        |

---

### 七、总结笔记

-   **机制**：`LPUSH` 入队，`BRPOP` 阻塞出队，Redis List 当缓冲区
-   **优点**：极简、复用 Redis、阻塞不空转
-   **缺点**：无 ACK、消息可能丢、不支持消费组、无死信
-   **定位**：轻量级、不重要的场景可以用；重要数据还是用 Redis Stream 或专业 MQ
