## Redis Pub/Sub 实现消息队列

---

### 一、核心模型

Pub/Sub（发布/订阅）和 List 完全不同：**List 是"一条消息一个人取"，Pub/Sub 是"一条消息所有订阅者都收到"**。

```
发布者                   Redis                    订阅者A
   │                      │                          │
   │  PUBLISH channel "msg"                          │
   │─────────────────────→│                          │
   │                      │── 消息广播 ──────────────→│
   │                      │                          │
   │                      │── 消息广播 ──────────────→│ 订阅者B
   │                      │                          │
   │                      │── 消息广播 ──────────────→│ 订阅者C
```

**关键区别：**

| 模式 | 类比 | 特点 |
|:---|:---|:---|
| List | 点对点聊天 | 消息只能被一个人取走 |
| Pub/Sub | 微信群广播 | 消息发给群里的所有人 |

---

### 二、基本命令

| 角色   | 命令                        | 说明                           |
| :--- | :------------------------ | :--------------------------- |
| 订阅者  | `SUBSCRIBE channel`       | 订阅一个频道                       |
| 发布者  | `PUBLISH channel message` | 向频道发消息                       |
| 退订   | `UNSUBSCRIBE channel`     | 取消订阅                         |
| 订阅模式 | `PSUBSCRIBE pattern`      | 按模式订阅，如 `PSUBSCRIBE order.*` |

**使用示例：**

```bash
# 终端1（订阅者）
SUBSCRIBE news
# 进入订阅状态，等待消息...

# 终端2（发布者）
PUBLISH news "hello"
# 返回：(integer) 1  ← 有1个订阅者收到了

# 终端1 收到：
# "message"
# "news"
# "hello"
```

---

### 三、Java 代码示例

```java
// 订阅者：需要独立的连接（订阅状态下连接只能收消息）
@PostConstruct
public void subscribe() {
    new Thread(() -> {
        stringRedisTemplate.execute((RedisCallback<Object>) connection -> {
            connection.subscribe((message, pattern) -> {
                String msg = new String(message.getBody());
                System.out.println("收到消息: " + msg);
                // 处理消息...
            }, "news".getBytes());
            return null;
        });
    }).start();
}

// 发布者
public void publish(String message) {
    stringRedisTemplate.convertAndSend("news", message);
}
```

### 四、Pub/Sub 的消息特征

**核心特性：消息不会被存储，是纯实时广播。**

```
发布消息的时刻
      │
      ├─ 此刻在线的订阅者 → 收到消息 ✅
      │
      └─ 此刻不在线的订阅者 → 永远收不到 ❌（消息不保留）
```

---

### 五、优缺点

#### 优点

| 优点        | 说明                           |
| :-------- | :--------------------------- |
| **天然一对多** | 一条消息所有订阅者同时收到                |
| **实时性强**  | 发布即推送，零延迟                    |
| **实现简单**  | `PUBLISH` / `SUBSCRIBE` 两个命令 |
| **低开销**   | 不存储消息，内存占用小                  |

#### 缺点

| 缺点 | 说明 |
|:---|:---|
| **消息不持久** | 订阅者不在线时消息**直接丢弃** |
| **无 ACK** | 收到消息后崩溃，消息找不回来 |
| **无积压能力** | 没有队列缓冲，发布多快就推多快 |
| **订阅者必须在线** | 无法"先存着，等会再消费" |
| **无消费组** | 无法实现"多个消费者轮流消费" |

**最致命的缺点：消息即发即丢。** 如果订阅者网络抖动、重启、处理慢，这期间的消息全部丢失。

---

### 六、适用场景

| 场景 | 是否适合 |
|:---|:---|
| 实时通知 / 广播 | ✅ 非常适合 |
| 缓存失效通知 | ✅ 适合 |
| WebSocket 消息推送 | ✅ 适合 |
| 离线消息 / 消息可靠性 | ❌ 完全不适合 |
| 削峰 / 缓冲 | ❌ 不适合（没有队列） |
| 多个消费者轮流处理 | ❌ 不适合 |

---

### 七、和 List 的对比

| 维度    | List          | Pub/Sub      |
| :---- | :------------ | :----------- |
| 消费模式  | **点对点**（一人取走） | **广播**（人人收到） |
| 消息存储  | 存着，等消费者取      | **不存**，即发即丢  |
| 消费者离线 | 消息还在队列里       | **消息丢失**     |
| 阻塞等待  | `BRPOP` 阻塞    | 订阅后连接一直收     |
| 削峰能力  | ✅ 有（队列积压）     | ❌ 无          |
| 一对多   | ❌ 不支持         | ✅ 天然支持       |
| 典型场景  | 任务队列          | 通知广播         |

### 八、Redisson 分布式锁中的 Pub/Sub 应用

你之前问的锁重试机制，Redisson 正是用 Pub/Sub 来通知等待线程：

```lua
-- 解锁 Lua 脚本最后一步
redis.call('publish', 'redisson_lock__channel:lock:order', threadId);
```

```
锁释放 → publish 消息到频道
                    ↓
所有等待这把锁的线程都订阅了这个频道
                    ↓
收到消息 → Semaphore.release() → 线程苏醒去抢锁
```

**这里 Pub/Sub 只做"通知唤醒"**，不做消息存储，锁重试的消息丢了也不影响（线程本身有超时兜底）。所以 Pub/Sub 的"不可靠"恰好不影响这个场景。

---

### 九、总结笔记

-   **机制**：`PUBLISH` 广播，`SUBSCRIBE` 订阅，消息不落盘不存储
-   **优点**：一对多广播、实时性好、实现简单
-   **缺点**：消息即发即丢、无 ACK、无缓冲
-   **定位**：适合实时通知场景，不能当可靠的消息队列 用
-   **典型应用**：缓存失效通知、分布式锁唤醒、聊天室广播
