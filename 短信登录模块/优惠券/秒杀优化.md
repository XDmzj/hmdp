# 优化

原流程：mysql承接了所有的查询请求，高并发的情景下，效率显著降低

![[Pasted image 20260812170254.png]]


优化：将判断库存和判断一人一单转接给redis执行，并且把订单的入库用另一个线程异步执行，
提高了并发效率
![[Pasted image 20260812171600.png]]





>优化前后对比

### 优化前（所有请求直连数据库）

```
用户请求 → 查数据库库存 → 查数据库订单（一人一单）→ 扣库存 → 创建订单
                ↑                    ↑                ↑
            全部同步执行，数据库扛所有并发压力
```

### 优化后（Redis 前置校验 + 异步落库）

```
用户请求 → Redis（Lua脚本原子校验：库存 + 一人一单）
              │
              ├─ 校验失败 → 直接返回 "已售罄" 或 "已下单"
              │
              └─ 校验成功 → 返回 "排队中" → 消息队列 → 异步线程落库
```



>两步优化的具体作用

第一步：Redis 前置校验
把**库存判断**和**一人一单判断**从数据库搬到 Redis，用 **Lua 脚本**原子执行

**好处：**
-   Redis 单线程，天然串行，Lua 脚本保证原子性
-   Redis QPS 能到 10 万级别，数据库只能到几千
-   绝大部分请求在 Redis 层就被拦截，不抵达数据库

第二步：异步下单
校验通过后，不直接写数据库，而是：
1.  返回给前端 "下单成功，处理中"
2.  把下单信息扔进**消息队列**（或线程池）
3.  后台异步消费者慢慢处理：扣减数据库库存 + 创建订单

**好处：**
-   **削峰填谷**：10000 个请求瞬间过来，Redis 校验通过 100 个，这些请求变成消息慢慢消费，数据库压力平滑
-   **解耦**：校验和下单两个动作不再绑定，前端秒级响应，后端慢慢处理
-   **最终一致性**：消息不丢，订单最终必然写入数据库
