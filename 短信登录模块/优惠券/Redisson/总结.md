## 一、完整演进路线

### 第 1 阶段：单体系统 + 一人多单 → 乐观锁

**场景**：单体应用，一个用户可以下多单。

**问题**：高并发下，多个线程同时查到库存 > 0，都去扣库存，导致超卖。

**方案**：乐观锁（CAS）

```sql
UPDATE product SET stock = stock - 1 
WHERE id = #{id} AND stock > 0
```

利用数据库的 `WHERE` 条件做版本检查，更新行数 = 0 就说明被别人改过了。

**局限性**：只适用于"查库存→扣库存"这类可以用一条 SQL 原子完成的场景。

---

### 第 2 阶段：单体系统 + 一人一单 → 悲观锁

**业务变更**：从"一人可以买多单"变成"一人只能买一单"。

**新问题**：乐观锁失效了。

-   乐观锁锁的是**库存行**，多个线程同时扣库存，只要 `stock > 0` 就能过
-   但"一人一单"的要求是**先查订单表有没有该用户的记录**，再插入订单
-   这是两个操作，无法用一条 SQL 原子完成

```
线程1：查订单表 → 用户A没有 → 准备插入
线程2：查订单表 → 用户A没有 → 准备插入
线程1：插入成功
线程2：插入成功 ← 一人一单被打破
```

**方案**：`synchronized` 悲观锁

```java
public synchronized Result createOrder(Long userId) {
    // 1. 查订单
    // 2. 没有 → 插入
    // 3. 返回
}
```

串行执行，同一时刻只有一个线程能进入。

**局限性**：`synchronized` 只能在**同一个 JVM** 内生效。

---

### 第 3 阶段：集群部署 → 分布式锁

**业务变更**：用户量激增，单体升级为集群（N 个 JVM）。

**新问题**：`synchronized` 失效。

```
JVM-1：线程1 拿到 synchronized 锁 → 查订单 → 没有 → 插订单
JVM-2：线程2 拿到 synchronized 锁 → 查订单 → 没有 → 插订单
                                    ↑ 两个 JVM，各锁各的，互不干扰
```

**方案**：分布式锁（Redis `SETNX`）

```java
// 加锁
Boolean lock = redis.setIfAbsent("lock:order:" + userId, "1");
// 解锁
redis.delete("lock:order:" + userId);
```

多个 JVM 都去 Redis 争同一个 Key，谁 `SETNX` 成功谁持有锁。

---

### 第 4 阶段：锁超时释放 → 线程标识

**问题**：基础版分布式锁没有过期时间，或者设了过期时间但被误删。

```
线程1：加锁成功，业务阻塞超过 10 秒 → 锁自动过期
线程2：趁虚而入，加锁成功
线程1：业务完成 → 执行 delete → 把线程2 的锁删了
线程3：趁虚而入...
```

**方案**：加锁时存线程标识，解锁时先判断是不是自己的锁。

```java
// 加锁：原子 SET + 过期时间
redis.setIfAbsent("lock:order:" + userId, threadId, 30, TimeUnit.SECONDS);

// 解锁：先判断再删除
String value = redis.get("lock:order:" + userId);
if (threadId.equals(value)) {
    redis.delete("lock:order:" + userId);
}
```

**局限性**：判断和删除不是原子操作。

---

### 第 5 阶段：判断与删除非原子 → Lua 脚本

**问题**：判断和删除之间有时间窗口。

```
线程1：GET → 判断成功 → [这里锁过期了] → DELETE → 删了线程2 的锁
```

**方案**：用 Lua 脚本把 GET + 判断 + DEL 打包成原子操作。

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
```

**局限性**：锁不可重入，同一线程再次 `lock()` 会自己阻塞自己。

---

### 第 6 阶段：不可重入 → Hash 结构 + 计数器

**问题**：同一个线程无法多次获取同一把锁。

**方案**：锁用 Hash 存储 `{线程标识: 重入次数}`。

```lua
-- 加锁
if (exists == 0) or (hexists == 1) then
    hincrby(key, threadId, 1);  -- 重入 +1
    pexpire(key, 30000);
end

-- 解锁
hincrby(key, threadId, -1);  -- 重入 -1
if (counter == 0) then
    del(key);  -- 完全释放
end
```

**此时你已经手动实现了一个"可重入的、原子的、有过期时间的"分布式锁。** 但还有问题：不可重试、不可自动续期。

---

### 第 7 阶段：Redisson → 一揽子解决所有问题

你发现自己造轮子永远追不上生产需求，于是引入 Redisson。

**Redisson 对应的解决方案：**

| 你遇到的问题 | Redisson 的解决方案 |
|:---|:---|
| 锁超时释放，业务没跑完 | **Watchdog** 自动续期，每 10 秒延长到 30 秒 |
| 不可重入 | **Hash 结构**，`state` 计数器自然支持可重入 |
| 不可重试（拿不到锁怎么办） | **Pub/Sub + Semaphore**，锁一释放立刻收到通知去抢 |
| 判断与删除非原子 | 所有操作封装在 **Lua 脚本**中原子执行 |
| 单节点锁不可靠 | **MultiLock / RedLock**，多节点多数派机制 |
| 等待时 CPU 空转 | **信号量阻塞**，不占 CPU |

**代码简化：**

```java
// 你之前写了一百多行的锁逻辑
// Redisson 三行搞定
RLock lock = redisson.getLock("lock:order:" + userId);
lock.lock();
try { ... } finally { lock.unlock(); }
```
