
# 缓存更新

## 数据一致性问题

缓存的使用降低了后端负载，提高了读写的效率，降低了响应的时间，这么看来缓存是不是就一本万利呢？答案是否定的！

并不是说缓存有这么多优点项目中就可以无脑使用缓存了，我们还需要考虑缓存带来的问题，比如：缓存的添加提高了系统的维护成本，同时也带来了数据一致性问题……总的来讲，系统使用引入缓存需要经过前期的测试、预算，判断引入缓存后带来的价值是否会超过引入缓存带来的代价


那么我们该如何解决数据一致性问题呢？首先我们需要明确数据一致性问题的主要原因是什么，从主要原因入手才是解决问题的关键！数据一致性的根本原因是 **缓存和数据库中的数据不同步**，那么我们该如何让 缓存 和 数据库 中的数据尽可能的即时同步？这就需要选择一个比较好的**缓存更新策略**了


## 缓存数据清理机制

>内存淘汰（全自动）。超时剔除（半自动）。主动更新（手动）。是什么？

这三个概念和你之前看的“更新策略”，本质上是**缓存生命周期管理中，解决同一问题（数据过期/失效）的不同维度与层级**。

把它们放在同一个框架下来看，逻辑就会非常清晰。

### 一、 整体全局视图：缓存数据治理的三道防线

缓存空间是有限的，而数据库的数据是无限且不断变化的。为了防止缓存被撑爆，以及防止缓存数据长期不一致，我们需要在**不同触发时机**下清理或更新缓存：

```
                    ┌─────────────────────────────────────────┐
                    │            缓存数据治理的三道防线         │
                    └─────────────────────────────────────────┘
                                         │
        ┌────────────────────────────────┼────────────────────────────────┐
        ▼                                ▼                                ▼
  【主动更新】                        【超时剔除】                      【内存淘汰】
  (业务触发 / 手动)                  (时间触发 / 半自动)              (容量触发 / 全自动)
  数据变更时，实时处理                给数据设置 TTL 存活期              内存满了，系统被迫清理
```

### 二、 详细拆解三者的区别与关系

 1. 主动更新（手动 / 业务驱动）

- **触发条件**：**数据发生变更时**（比如用户修改了密码、商品更新了价格）。
    
- **本质**：由**业务代码**主动发起的更新或删除动作。
    
- **角色**：上一条回答中提到的 **Cache-Aside（旁路缓存）**、**Write-Through** 等，**全都属于“主动更新”的具体实现模式**。
    
- **特点**：
    
    - **实时性最高**：尽可能保证数据库变更后，缓存立刻失效或更新。
        
    - **开发成本高**：需要写代码去控制“何时更新、先更新数据库还是先删缓存”。

 2. 超时剔除（半自动 / 时间驱动）

- **触发条件**：**数据达到了预设的存活时间（TTL，Time To Live）**。
    
- **本质**：给缓存设置一个“保质期”（比如 `redis.set(key, value, expire=300s)`）。
    
- **角色**：**主动更新的“保底兜底”机制**。
    
    - 就算你的“主动更新”因为代码 bug、网络抖动或 MQ 延迟导致删缓存失败，到了 TTL 时间，系统也会把旧缓存清理掉，确保**最终一致性**。
        
- **为什么叫“半自动”**：
    
    - **人工定义规则**：你需要手动指定该 Key 存活 5 分钟还是 1 小时。
        
    - **系统自动执行**：一旦设好 TTL，后续的过期清理（如 Redis 的定期删除 + 惰性删除）完全由缓存系统底层自动完成，不需要你写代码去监控。

 3. 内存淘汰（全自动 / 资源驱动）

- **触发条件**：**缓存占用的内存达到了设置的物理上限（maxmemory）**。
    
- **本质**：缓存系统的**自我保护机制**（防止 OOM 导致服务崩溃）。
    
- **角色**：**系统生存的“最后防线”**。
    
    - 无论数据有没有过期、有没有主动更新，只要内存满了，缓存系统就必须强行扔掉一部分数据来腾出空间。
        
- **为什么叫“全自动”**：
    
    - 你只需要在配置文件里选一个策略（比如 LRU 最近最少使用、LFU 最不经常使用、Random 随机等），后续所有强行清理动作完全由 Redis/Memcached 底层引擎全权接管，对上层业务代码完全透明。  

### 三、 三者的对比总结

| **维度**   | **主动更新**     | **超时剔除**         | **内存淘汰**          |
| -------- | ------------ | ---------------- | ----------------- |
| **驱动力**  | 业务逻辑（数据改了）   | 时间（保质期到了）        | 资源限制（内存满了）        |
| **掌控度**  | 完全由开发者控制     | 开发者设规则，系统执行      | 完全由缓存中间件接管        |
| **核心目的** | 保障数据**实时一致** | 保障数据**最终一致**（兜底） | 保障系统**服务可用**（不崩溃） |
| **数据损失** | 无损失，配合业务     | 无损失，属于正常过期       | **有损失**，可能踢掉高频热点  |

### 四、 生产环境中的组合使用

在实际开发中，这三者**绝不是互斥的，而是同时叠加使用的**：

1. **配置【内存淘汰】**：设置 Redis 最大的内存使用量，配置淘汰策略为 `allkeys-lru`（保护 Redis 不宕机）。
    
2. **写代码【主动更新】**：采用 Cache-Aside 模式，更新数据库后，手动执行 `redis.del(key)`（保证绝大多数情况下数据一致）。
    
3. **设置【超时剔除】**：写入缓存时，必须带上一个合理的 TTL（比如 30 分钟），防止因为偶发的“删缓存失败”导致缓存里永久留着脏数据。


## 缓存更新策略

**缓存更新策略**：只是**主动更新**这一块的专属名称。

在高并发和分布式系统中，缓存与数据库的一致性是核心难题之一。常见的缓存更新策略主要有以下 **4 种设计模式**，各自适用不同场景。

### 1. Cache-Aside Pattern（旁路缓存模式）

最常用的策略，缓存维护逻辑由**业务代码直接控制**。

1.操作逻辑

- **读流程**：先读缓存；若命中则直接返回；若未命中，则从数据库读取，写入缓存后返回。
    
- **写流程**：**先更新数据库，再删除缓存**（不是更新缓存）。
    

```
[读操作] 客户端 -> 查缓存 -未命中-> 查数据库 -> 写入缓存 -> 返回
[写操作] 客户端 -> 更新数据库 -> 删除缓存
```

2.关键争议与解析

- **为什么是“删除缓存”而不是“更新缓存”？**
    
    - **并发安全**：若两个写请求 A 和 B 并发执行，如果采用“更新缓存”，可能出现 `写DB-A -> 写DB-B -> 更新缓存B -> 更新缓存A` 的情况，导致缓存变成旧值 A。
        
    - **资源开销**：如果写操作频繁，而读操作较少，每次写都更新缓存会导致大量无效计算（很多写入的缓存还没被读过就被再次覆盖）。
        
- **为什么是“先更新 DB，再删缓存”而不是反过来？**
    
    - 若先删缓存，在更新 DB 期间，有读请求进来发现缓存为空，就会把 DB 中的旧数据查出来重新写入缓存，导致后续全部读到脏数据。
        

> **注意极端并发边界**：在“先更新 DB 再删缓存”模式下，理论上也存在脏数据概率（读未命中 + 读 DB 耗时 > 写 DB 耗时 + 删缓存 耗时），但实际生产中极罕见。若对绝对一致性有要求，需配合**延迟双删**或**分布式锁**。

3.选择先更新数据库，再删除缓存。那么如何保证缓存与数据库的操作的原子性（同时成功或失败）？

 对于单体系统，将缓存与数据库操作放在同一个事务中（当前项目就是一个单体项目，所以选择这种方式）
 对于分布式系统，利用TCC（Try-Confirm-Cancel）等分布式事务方案



### 2. Read-Through Pattern（读穿透模式）

将缓存和数据库的交互封装为一个统一的服务（Cache Provider）。业务层只和缓存打交道，不需要关心底层数据库。

- **读流程**：业务方直接请求缓存服务，若缓存缺失，由**缓存服务自行从 DB 加载数据**并写入缓存，最后返回给业务方。
    

### 3. Write-Through Pattern（写穿透模式）

写操作同样由缓存服务统一代理。

- **写流程**：业务方调用缓存服务更新数据，缓存服务**同步更新缓存和数据库**，两步均成功后才返回成功。

> Read-Through 和 Write-Through 通常配合使用，常见于使用本地缓存组件或特定的中间件服务封装。

### 4. Write-Behind Pattern（写回/异步刷盘模式）

- **写流程**：业务方（调用者）更新数据时，**只更新缓存并直接返回成功**。缓存服务通过后台异步批量将数据刷入数据库（例如延迟 5 秒或凑满 100 条批量写入）。
    
- **优缺点**：
    
    - **优点**：写入性能极高，适合高频写场景（如计数器、日志收集）。
        
    - **缺点**：强烈依赖缓存可用性，若缓存宕机，未刷盘的数据会永久丢失。
        

### 策略对比与选型指南

|**策略**|**写延迟**|**数据一致性**|**实现复杂度**|**典型适用场景**|
|---|---|---|---|---|
|**Cache-Aside**|低|最终一致|低（应用层实现）|通用业务（电商商品、用户信息）|
|**Read/Write-Through**|中|最终一致|中（需封装组件）|框架统一抽象、屏蔽底层的业务系统|
|**Write-Behind**|极低|存在丢数据风险|高|高频写、对数据丢失不敏感（点赞数、浏览量）|

### 保证一致性的补充方案

如果使用的是 **Cache-Aside**，在分布式环境下要保障“删缓存”步骤成功，通常采用以下手段：

1. **延迟双删**：写 DB 前删一次缓存，更新完 DB 后**异步等待一段时间（如 500ms）再删一次缓存**，用以清除在更新 DB 期间可能被写入的旧缓存。
    
2. **基于 Binlog 异步删除**：业务更新 DB 后不做缓存处理，由单独的服务（如 Canal）监听 MySQL 的 Binlog 变更日志，异步将删除消息投递到 MQ，再由消费者删除缓存。这种方式实现了业务代码与缓存清理逻辑的解耦。

### 应用场景
在主动更新的 3 种设计模式中，它们本质上是在**数据一致性**、**写性能/响应速度**和**系统复杂度**之间做权衡。

下面是这三种方案的典型应用场景及其背后的设计原因：
1. Cache-Aside Pattern（旁路缓存模式）

 典型应用场景
- **常规业务系统**：电商商品详情、用户个人资料、新闻文章、内容管理系统（CMS）。
- **读多写少**的通用场景。

 为什么选它？
- **写性能损耗小**：写操作只需要处理数据库和**删除**缓存（甚至只在读未命中时才写缓存）。如果采用更新缓存，当一个数据被频繁修改却极少被读取时，会导致大量无效的缓存写入。
- **逻辑可控、实现简单**：应用代码直接掌控一切，不需要额外部署或改造专门的缓存代理层。
- **高容错性**：如果 Redis/缓存层暂时挂掉，应用可以直接降级去查数据库，系统依然可用，不会因为缓存组件崩溃导致整个写流程直接报错。


2. Read-Through / Write-Through Pattern（读/写穿透模式）

 典型应用场景
- **分布式缓存中间件 / 基础架构层**：如 Spring Cache 结合 Redis、Guava Cache / Caffeine 本地缓存组件。
- **业务逻辑层想与数据存储解耦的系统**：应用开发人员不想在业务代码里充斥着 `if(cache == null)` 和 `redis.del()` 的冗余逻辑

 为什么选它？
- **代码简洁，屏蔽细节**：将“缓存与 DB 的同步”下沉为独立的底层服务。应用层只需要调用 `cache.get(key)` 或 `cache.put(key, val)`，就像在使用一个“容量无限大且超快的数据库”一样。
- **避免脏数据和并发冲突**：由于所有的读写都收拢到统一的缓存服务代理，更容易在代理层内部通过加锁、排队等机制解决并发写导致的缓存不一致问题。


 3. Write-Behind Pattern（写回 / 异步刷盘模式）
 
 典型应用场景
- **超高频写的统计与计数场景**：视频播放量、文章阅读数、社交点赞数、游戏实时排行榜。
- **日志与轨迹收集**：用户行为埋点收集、高频轨迹数据暂存。

 为什么选它？
- **极极致的写性能与吞吐量**：写操作**完全发生在内存**中，响应时间在毫秒甚至微秒级。
- **数据库写压力的“削峰填谷”**：利用合并写入（如合并 100 次 `+1` 操作为一次 `+100` 的 SQL 更新），将高并发的散碎写请求转化为低频的批量写请求，极大地保护了关系型数据库。

> **核心代价**：由于数据先存内存、异步落盘，**牺牲了强一致性和安全性**。一旦缓存节点突发宕机，未刷盘的数据会直接丢失。因此它绝对不能用于交易、订单、余额等核心数据。


 总结选型对照表

|**模式**|**核心侧重点**|**读/写性能**|**风险与代价**|
|---|---|---|---|
|**Cache-Aside**|简单通用、容错率高|读快，写正常|业务代码需显式维护缓存逻辑|
|**Read/Write-Through**|业务解耦、透明抽象|读快，写正常（取决于 DB 写入）|需要额外封装/集成代理组件|
|**Write-Behind**|极致写性能、削峰|**读极快，写极快**|宕机**存在丢数据风险**，实现复杂|
