在开发中使用缓存（如 Redis）时，最常面对的就是**缓存的三大经典问题**（有时被称为“缓存三剑客”）：**缓存穿透**、**缓存击穿** 和 **缓存雪崩**。

### 一、 缓存穿透 (Cache Penetration)

#### 1. 什么是缓存穿透？

指的是查询一个**既不在缓存中，也不在数据库中**的数据（比如查询 `id = -1` 的商品）。

每次请求过来：

1. 查缓存 $\rightarrow$ 没查到；
    
2. 查数据库 $\rightarrow$ 也没查到（返回空）；
    
3. 结果**无法写入缓存**。
    

如果有恶意攻击者用这种不存在的 Key 发起海量请求，所有请求都会**穿透**缓存直接打在数据库上，导致数据库瘫痪。

```
[请求 id=-1] ──> [Redis 查无此 Key] ──> [MySQL 查无此数据] ──> (无法建立缓存)
      ▲                                       │
      └─────────────────海量攻击打爆数据库───────┘
```

#### 2. 解决方案

- **方案一：缓存空对象（常用、实现简单）**
    
    - 当数据库查询结果为空时，依然把这个 `null` 或空对象写入 Redis，并设置一个较短的过期时间（如 2~5 分钟）。
        
    - _优点_：简单粗暴。
        
    - _缺点_：额外占用 Redis 内存；可能存在短期的“缓存与数据库数据不一致”问题。
        
- **方案二：布隆过滤器（Bloom Filter，适合海量数据）**
    
    - 在访问 Redis 之前加一层布隆过滤器。利用高效的哈希算法和位图结构，快速判断该 Key **是否可能存在**。如果布隆过滤器判定不存在，直接拦截返回，不再往下查。
        
    - _优点_：内存开销极小。
        
    - _缺点_：实现相对复杂；存在误判率（判定“存在”不一定真存在，但判定“不存在”则一定不存在）；不支持删除元素。

```java
    /**
     * 根据id查询商铺数据
     *
     * @param id
     * @return
     */
    @Override
    public Result queryById(Long id) {
        String key = CACHE_SHOP_KEY + id;
        // 1、从Redis中查询店铺数据
        String shopJson = stringRedisTemplate.opsForValue().get(key);

        Shop shop = null;
        // 2、判断缓存是否命中
        if (StrUtil.isNotBlank(shopJson)) {
            // 2.1 缓存命中，直接返回店铺数据
            shop = JSONUtil.toBean(shopJson, Shop.class);
            return Result.ok(shop);
        }

        // 2.2 缓存未命中，判断缓存中查询的数据是否是空字符串(isNotBlank把null和空字符串给排除了)
        if (Objects.nonNull(shopJson)){
            // 2.2.1 当前数据是空字符串（说明该数据是之前缓存的空对象），直接返回失败信息
            return Result.fail("店铺不存在");
        }
        // 2.2.2 当前数据是null，则从数据库中查询店铺数据
        shop = this.getById(id);

        // 4、判断数据库是否存在店铺数据
        if (Objects.isNull(shop)) {
            // 4.1 数据库中不存在，缓存空对象（解决缓存穿透），返回失败信息
            stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.SECONDS);
            return Result.fail("店铺不存在");
        }
        // 4.2 数据库中存在，重建缓存，并返回店铺数据
        stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop), 
                                              CACHE_SHOP_TTL, TimeUnit.MINUTES);
        return Result.ok(shop);
    }

```

第一次查询数据库中和缓存中不存在的数据，请求经过了数据库，但是缓存了空字符串
第二次查询（短期内），发先请求未经过数据库，redis直接返回null

### 二、 缓存击穿 (Cache Breakdown)

#### 1. 什么是缓存击穿？

指的是一个**热点 Key**（比如微博热搜、秒杀爆款商品），在**高并发访问**的瞬间突然**过期失效**了。

此时，瞬间倾泻而来的成千上万个并发请求在 Redis 中都没查到数据，会**同时**冲向数据库去加载数据并回写缓存。数据库瞬间承受巨大的并发压力，极易被直接打垮。

> **比喻**：像是在一块高密度防弹玻璃（Redis）上突然打穿了一个小洞，所有的子弹（并发请求）瞬间顺着这个小洞射向后面的墙壁（MySQL）。

#### 2. 解决方案

- **方案一：互斥锁（分布式锁，如 Redisson）**
    
    - 当缓存失效时，不让所有线程都去查库。只有拿到分布式锁的**第一个线程**有资格去数据库查数据并更新 Redis，其他线程等待或重试。
        
    - _优点_：保证数据强一致性，不会产生冗余查询。
        
    - _缺点_：会导致其他线程等待，降低整体吞吐量；存在死锁风险。
        
- **方案二：逻辑过期（永不过期 + 异步更新）**
    
    - 在 Redis 的 Value 中人为添加一个字段 `expire`（逻辑过期时间），Redis 本身**不设置真实的过期时间（TTL）**。
        
    - 线程查询时，发现逻辑时间已经过期，**不阻塞当前请求**（直接返回旧数据），同时开一个**异步线程**去获取锁、查库并更新 Redis。
        
    - _优点_：性能极高，用户无感知（响应快）。
        
    - _缺点_：在异步更新完成前，用户读到的是短暂的**旧数据**（牺牲一致性换取可用性）。
        

### 三、 缓存雪崩 (Cache Avalanche)

#### 1. 什么是缓存雪崩？

指的是在同一时间段内，**大量缓存 Key 集中失效过期**，或者 **Redis 节点整体宕机/崩溃**。

当大量请求涌入时，Redis 无法提供服务，所有的请求像雪崩一样全部砸向数据库，导致数据库连环崩塌，整个系统瘫痪。

#### 2. 解决方案

- **针对“大量 Key 集中过期”：**
    
    - **随机化 TTL**：给每个 Key 的过期时间加上一个**随机偏差值**（例如固定 30 分钟 + 1~5 分钟的随机数），防止同一时刻大量 Key 同时失效。
        
    - **热点数据预热**：在活动开始前，提前将热点数据写入缓存，并分散设置 TTL。
        
- **针对“Redis 实例宕机/故障”：**
    
    - **构建高可用 Redis 集群**：采用 Redis Sentinel（哨兵）模式或 Redis Cluster（集群）模式，实现主从复制和故障自动转移。
        
	- **服务熔断与降级**：**限流（Rate Limiting）**：通过网关（如 Sentinel、Nginx、Spring Cloud Gateway）限制进入系统的总 QPS。超出数据库承载极限的请求直接拒绝（返回友好提示“系统繁忙”）。      **熔断与降级（Circuit Breaking & Fallback）**：当检测到 DB 响应超时或错误率飙升时，触发熔断，暂时关闭部分非核心业务，直接返回本地默认值或缓存兜底数据，优先保证主流程可用。
        
    - **多级缓存架构**：结合 JVM 本地缓存（如 Caffeine），即使 Redis 宕机，本地缓存还能扛住一部分流量。
        

### 三大问题总结对比表

|**问题类型**|**核心原因**|**损害目标**|**核心应对策略**|
|---|---|---|---|
|**缓存穿透**|查询了**不存在**的数据|数据库|缓存空对象 (`null`) / 布隆过滤器|
|**缓存击穿**|**单个热点 Key** 突然过期|数据库|互斥锁（保证强一致） / 逻辑过期（保证高可用）|
|**缓存雪崩**|**大量 Key** 集中过期 / Redis 宕机|数据库及整个系统|过期时间加随机数 / 搭建 Redis 高可用集群 / 熔断限流|
